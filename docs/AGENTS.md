# Agents

Every agent is generated by `orgtomo sync` from a template in `agents-src/` plus your configuration. This page describes what each one is given.

## What an agent is made of

| Part | Source | Notes |
|---|---|---|
| Role prompt | `agents-src/<name>.md` | Mission, method, limits, output |
| Model and effort | `agents.yaml` | Per agent; change with `/orgtomo:models`, the UI, or the file |
| Tools | `capabilities.yaml` grants | Built-in tools listed there, plus the tools of each granted capability |
| Playbook skills | `skills-src/` | Preloaded in full at start |
| Org style skills | generated from `conventions.yaml` | `org-naming`, `org-comments`, `org-format` for agents that write or judge code |
| Lessons skill | generated from approved lessons | `lessons-<agent>`; empty until something real has been learned |
| Salesforce skills | `capabilities.yaml` `sf_skills` | Named in the prompt, loaded on demand from the pinned Salesforce plugins |
| Guards | plugin hooks | Apply to every tool call, by agent identity |
| Contract | `spec/schemas/` | The shape its JSON output must have |

### Memory

Agents have no free-form memory file. Notes an agent writes for itself are unverified, and an unverified note that is reloaded forever is exactly how wrong beliefs settle in. What persists instead:

- the **Org Brain** (generated facts with source hashes),
- the **ticket folder** (contracts, gate reports, evidence),
- the **lessons skill** (each lesson cites recorded observations and is approved by you or by enough evidence).

## Support agents

| Agent | Default | Job | Switch |
|---|---|---|---|
| Baseline | sonnet / low | Backups and existing test results before the build | `agents.yaml` or `/orgtomo:features baseline off` |
| Scribe | sonnet / low | Drafts of tracker comments and chat messages, fitted to the reader; never posts | same |
| Coach | sonnet / medium | Lessons from recorded observations at the close stage | same |
| Notetaker | sonnet / low | Meeting notes into the vault; only with the meetings feature | `/orgtomo:features meetings on` |

When Baseline is off, the Builder still cannot deploy without a backup, and the regression gate reports "skipped" visibly.

## Models and effort

`agents.yaml`:

```yaml
agents:
  reviewer: { model: fable, effort: high, enabled: true, core: true }
rules:
  reviewer_differs_from_builder: true
```

- `model`: `sonnet`, `opus`, `haiku`, `fable`, `inherit`, or a full `claude-...` id.
- `effort`: `low`, `medium`, `high`, `xhigh`, `max`. Available levels depend on the model.
- From Claude Code: `/orgtomo:models planner opus xhigh`, or just `/orgtomo:models tester high` to change effort only.
- Changes take effect in the next session; `orgtomo sync` runs automatically.

The defaults put the strongest reasoning where a wrong step is most expensive (reproduction and planning) and a different model on review.

## The Lead's verification

After a stage passes its gates, `orgtomo next` asks the Lead to verify when the stage has `lead_verify: true` (understand, repro, plan, build, test; on the lite path only build). The engine accepts the check only if:

- the claim exists in the stage's contract,
- the evidence was created after the submission,
- the evidence was produced by the Lead itself.

`--result mismatch` fails the stage and is recorded as a mistake of the owning agent.

## The lite path

Tickets that are small, low-risk and configuration-only take lighter reproduction and review. The engine decides from the Analyst's contract: `lite_candidate`, `risk: low`, at most `lite.max_components` affected components, all of types in `lite.allowed_types`. The gates are the same on both paths. On the lite path the Reproducer and Reviewer work in light mode (one scenario; core rubric items) and the Lead verifies the build stage only.

## Changing an agent

- Behaviour for your org: prefer `/orgtomo:rule <agent> <rule>`; it becomes a lesson with a record of who said it.
- Tools: `capabilities.yaml`.
- The role itself: edit the template in `agents-src/` (in a fork) and run `orgtomo sync`.
